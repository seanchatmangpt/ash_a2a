# v26.9.17 CommandBus Scale: Memory/InMemory vs. Ekv, Receipt Store and Authority Broker

Real comparative benchmark answering one question: does swapping
`AshA2A.CommandBus.run/4`'s receipt store from the default
`AshA2A.ReceiptStore.Memory` (a single `GenServer`, one mailbox, every
concurrent claim/commit funneled through it) to `AshA2A.ReceiptStore.Ekv`
(a real on-disk `:ekv` instance using per-key CAS, `if_vsn:`, for claim
atomicity -- no shared mailbox, no cross-`command_id` contention) resolves
the climbing-tail-latency-under-sustained-load characteristic a prior
session pass measured for `CommandBus.run/4` against `Memory`. Both stores
are real, already-implemented, already-tested modules in this codebase
(`lib/ash_a2a/receipt_store/memory.ex`, `lib/ash_a2a/receipt_store/ekv.ex`)
-- this document reports what a real side-by-side run of both actually
shows, not a hypothesis about what should happen.

A second, structurally analogous real benchmark asks the same question one
layer up, at the `AshA2A.Authority.Broker` used by
`AshA2A.Agent.build_command/4` -> `Authority.Grant.authorize/3` ->
`broker.granted?/3`: does `AshA2A.Authority.Broker.Ekv` resolve a bottleneck
relative to `AshA2A.Authority.Broker.InMemory` (also a single-`GenServer`
reference implementation) the same way the receipt-store comparison above
hypothesized? See "Authority Broker" below -- its real answer is
**no, not even the qualified way the receipt store's Ekv comparison partly
resolved.**

## Method

Two structurally identical stress tests, differing in exactly one real
variable (which `AshA2A.ReceiptStore` backend every `CommandBus.run/4` call
funnels its claim/commit through):

- `test/ash_a2a/chicago/stress/sustained_throughput_test.exs` --
  `AshA2A.ReceiptStore.Memory` (pre-existing).
- `test/ash_a2a/chicago/stress/sustained_throughput_ekv_test.exs` --
  `AshA2A.ReceiptStore.Ekv`, started via `start_supervised!({EKV, name:
  ekv_name, data_dir: <real tmp dir>, cluster_size: 1})`, the same
  real-local-EKV pattern `test/ash_a2a/receipt_store_ekv_test.exs` already
  uses (new; added by this document's own change).

Both drive the identical real consequence path -- `CommandBus.run/4` ->
`admit/2` (reads `command.authority` directly; `AshA2A.Authority.Broker` is
not consulted at this layer, so it is not implicated in either number below)
-> claim -> actuation claim -> receipt anchor -> real `Ash.create` against a
real `Ash.DataLayer.Ets`-backed `AshA2A.Test.Fixture.Item` -> postcondition
-> commit -- with `System.schedulers_online() = 16` real concurrent BEAM
worker processes issuing genuinely distinct commands continuously for a real
12,000 ms window, measured with the same `AshA2A.Chicago.Bench.distribution/1`
/ `per_second/2` harness and the same first-half-vs-second-half real
wall-clock bucketing. Three real runs of each, back to back, same host,
same session.

## What the real numbers show

**The degradation-ratio hypothesis is confirmed for p99, not decisively for
p50.** Memory's `degradation_ratio_p99` is consistently and substantially
above 1 across all three runs (1.27x-1.52x) -- late-window p99 tail latency
is reliably worse than early-window p99 under sustained load, the real
climbing-tail-under-load signature this benchmark exists to detect. Ekv's
`degradation_ratio_p99` sits at or below 1 in two of three runs (1.07x,
1.04x) and *below* 1 in the third (0.81x) -- no reliable climbing pattern.
`degradation_ratio_p50` is not a clean discriminator either way at this
sample size: Memory's ranges 0.96x-1.06x (essentially flat), Ekv's ranges
1.01x-1.15x (also essentially flat, marginally higher) -- p50 does not
climb meaningfully under sustained load for *either* store in these runs,
so p50 is not where Memory's single-mailbox serialization cost shows up;
p99 is.

**Ekv does not resolve tail latency in the unqualified sense -- it trades
one real bottleneck shape for a different one.** Absolute throughput under
Ekv is 22%-53% lower than Memory across matched runs (Ekv: 738-1,259/s;
Memory: 1,460-1,582/s), and absolute latency at every percentile is higher
under Ekv than under Memory in every run pair. Most decisively: Ekv run 3
produced a single dispatch with **2.37 seconds** of real latency (and
another over 1.9s) -- roughly 13x-20x worse than Memory's worst observed max
across all three of its runs (117-189 ms). This is consistent with real
on-disk EKV write-path I/O stalls under concurrent CAS contention (16
workers writing distinct keys to one EKV instance backed by real disk I/O,
on a host already under real load-average-13 contention from unrelated
processes) rather than a per-key-CAS defect -- the per-key CAS mechanism
itself did its job (zero errors, zero replays, zero command_conflicts across
all three Ekv runs; every sampled receipt round-tripped through a real
`Ekv.fetch/2` against the actual on-disk instance). The cost moved from "a
shared mailbox queues up predictably as the run continues" (Memory) to "a
shared disk resource can stall unpredictably under concurrent write
pressure" (Ekv) -- a different real bottleneck, not the absence of one, and
the task's own instruction to verify rather than assume the hypothesis
anticipated exactly this possibility.

## Authority Broker: InMemory vs. Ekv

Real, separate benchmark (`test/ash_a2a/chicago/stress/agent_dispatch_broker_scale_test.exs`)
drives the real `AshA2A.Agent.build_command/4` dispatch layer -- 16 workers,
6 real seconds per phase, zero errors either phase -- against
`AshA2A.Authority.Broker.InMemory` and `AshA2A.Authority.Broker.Ekv` in
turn, each backing real per-principal grant lookups
(`Authority.Grant.authorize/3` -> `broker.granted?/3`) for a real
`AshA2A.Test.Fixture.Item`-backed agent. Unlike the receipt-store
comparison above, this is a **read-heavy** path (a grant is written once
per principal/capability and then read on every dispatch), so it exercises
a structurally different real bottleneck shape.

| Metric | InMemory | Ekv | Ekv/InMemory ratio |
|---|---|---|---|
| `ok_count` (real dispatches) | 5,137 | 2,833 | -- |
| `throughput_per_second` | 852.61 | 468.11 | 0.549x |
| `p50` (us) | 16,382 | 28,981 | 1.769x |
| `p90` (us) | 23,262 | 50,185 | 2.157x |
| `p95` (us) | 27,708 | 61,919 | -- |
| `p99` (us) | 60,623 | 101,067 | 1.667x |
| `max` (us) | 216,659 | 228,029 | -- |
| `error_count` (either phase) | 0 | 0 | -- |

**Ekv does not resolve a bottleneck at this layer -- it is measurably
worse, unambiguously, at every measured percentile.** Unlike the
receipt-store result above (a real, qualified win on the specific climbing-
p99 pattern, offset by worse absolute numbers), there is no qualified win
to report here: Ekv is 1.7x-2.2x higher latency and runs at roughly half
the throughput of InMemory, consistently. The real, disclosed reason is the
structural difference between the two access patterns this document's two
benchmarks exercise: the receipt store's bottleneck is **write** contention
(every concurrent command claims/commits through the same shared resource),
which per-key CAS genuinely parallelizes; the authority broker's cost here
is **read** latency (a real on-disk `EKV.get/2` round-trip per dispatch vs.
an in-process `GenServer` map read), and per-principal grant reads have no
cross-principal write contention for `InMemory`'s single mailbox to
serialize under in the first place -- so there is no shared-mailbox
bottleneck for `Ekv`'s CAS mechanism to relieve at this layer, only real
I/O latency it adds. This is a genuine, disclosed architectural trade
(`Ekv`'s only real advantage here is durability across a process/node
restart, exactly as for the receipt store), not a defect: zero errors,
zero replays, zero conflicts in every phase of every run.

## Real gap found and fixed: the Ekv broker's config-only claim was not true

Investigating *why* production callers might reach for `Authority.Broker.Ekv`
despite the numbers above (durability, not speed) surfaced a real,
independent gap this task closed: `docs/how-to/authenticate-agent-requests.md`'s
own primary example --

```elixir
config :ash_a2a, :authority_policy, :broker
config :ash_a2a, :authority_broker, AshA2A.Authority.Broker.Ekv
```

-- was not actually config-only. `AshA2A.Authority.Broker.Ekv`'s own
moduledoc states it plainly: "this module does not start or supervise `EKV`
itself -- a real, already-running `EKV` instance ... must already exist
... before `issue/3`, `revoke/2`, or `verify/2` are called." Meanwhile
`AshA2A.Application.start/2` already auto-starts a real `EKV` instance for
`:receipt_store` (`receipt_store_children/0`, wired since the store was
introduced) but had **no equivalent clause for `:authority_broker`** -- so
a host that set only the config above, with no separate supervision-tree
change of their own, got every real `granted?/3` call rescuing/catching to
`false` ("broker unavailable") the moment traffic arrived, not the fail-
open-looking-but-actually-silent behavior the doc's own wording implied.

Fixed in `lib/ash_a2a/application.ex`: a new `authority_broker_children/0`,
mirroring `receipt_store_children/0` exactly, starts a real, distinctly-
named-and-pathed `EKV` instance (`{EKV, AshA2A.Authority.Broker.Ekv}`,
default `data_dir` under `System.tmp_dir!/0`, overridable via
`config :ash_a2a, :authority_broker_ekv_opts, [...]`, the same convention
`:receipt_store_ekv_opts` already uses) whenever `:authority_broker`
resolves to `AshA2A.Authority.Broker.Ekv` (bare module or `{module, opts}`
tuple form, matching `AshA2A.Authority.Grant.resolve_broker/1`'s own
normalization). `AshA2A.Authority.Broker.InMemory` deliberately keeps its
existing host-started convention (this project's own `test/test_helper.exs`
starts it explicitly, matching the broker's own moduledoc) -- only the
durable `Ekv` broker needed this fix, and choosing both `:receipt_store`
and `:authority_broker` as `Ekv` at once now correctly starts two distinct
`EKV` instances (verified by a real test below), never one shared instance
silently reused for both.

Proven by two new, real (no mock/stub) tests in
`test/ash_a2a/application_test.exs`: one starts the real application with
only `config :ash_a2a, :authority_broker, AshA2A.Authority.Broker.Ekv` set,
then round-trips a real grant through `AshA2A.Authority.Grant.grant/3` /
`granted?/3` / `revoke/3` -- the exact real production entry point, not the
broker module called directly -- with no manual `EKV` start anywhere in the
test; the other configures both layers as `Ekv` simultaneously and asserts
two distinct, real, alive `EKV` children with different ids. Both pass
repeatably (5 consecutive runs, 4 additional runs across distinct
`--seed` values, 0 failures) after fixing two real defects the tests
themselves caught while being written: an `EKV.child_spec/1` type
assertion (`:supervisor`, not `:worker`), and directory-name and
grant-subject uniqueness that a bare `System.unique_integer/1` does not
guarantee ACROSS separate `mix test` process invocations -- both are the
kind of gap real tests are supposed to catch, and did.

## Conclusion: how should a production caller configure this?

`config :ash_a2a, :receipt_store, AshA2A.ReceiptStore.Ekv` is the correct
choice when receipts durably surviving a process/node restart is a real
requirement (`Ekv.durable?/0 -> true`; `Memory` cannot make this claim at
all) -- that durability property is unconditional and this benchmark does
not change it. For the specific *tail-latency-under-sustained-load* question
this document was built to answer: Ekv measurably resolves the *climbing*
p99 pattern (late-window tail predictably worse than early-window tail)
that Memory shows, but at the cost of materially lower steady-state
throughput and -- on this shared, disk-contended host -- occasional
multi-second real outliers that Memory's runs never produced at all. A
production caller choosing Ekv purely to fix scale/tail-latency (not for
durability) should not assume it is a strict latency improvement; it should
provision a real, low-contention `:data_dir` (a dedicated volume, not a
shared/loaded host's tmp filesystem) and independently benchmark against
its own expected concurrency and disk characteristics before relying on
this result at a different scale or on different hardware. Neither store's
numbers here should be read as this codebase's ceiling -- both are read as
measured, on one real shared host, under one real load shape, three runs
each.

For `:authority_broker`, the recommendation is more direct:
**`AshA2A.Authority.Broker.Ekv` is a durability choice, not a scale choice.**
Choose it only when surviving a process/node restart without losing
issued/revoked grant state is a real requirement for this deployment; choose
it, and now (post-fix) it is genuinely config-only, with automatic `EKV`
wiring matching the receipt store's own. Choose `InMemory` (the default,
already what `config/test.exs` and this project's own test suite use) when
that durability is not needed -- it is measurably faster and higher-
throughput at this specific, read-heavy layer, not merely "the simple
option." A production deployment with real durability requirements on both
layers should expect the combined real cost this document measures: Ekv's
receipt-store trade (a real, qualified win on climbing tail latency, offset
by worse absolute numbers and occasional multi-second I/O-contended
outliers on a loaded host) plus Ekv's authority-broker trade (a
straightforward ~1.7x-2.2x latency cost with no qualifying upside, at this
layer, in these runs) -- both real, disclosed, and neither hidden behind an
unqualified "Ekv is the scale answer" claim.
