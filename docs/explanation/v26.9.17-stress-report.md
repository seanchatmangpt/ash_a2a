## Sustained CommandBus.run/4 throughput (worktree: stress-sustained-throughput)

**Subject**: `AshA2A.CommandBus.run/4`, driven end to end -- target
resolution, preflight, admission (a real `AshA2A.Authority` struct attached
to each command, checked by `admit/2`, not a broker lookup at this layer),
kill-switch check, claim, actuation claim, receipt anchor, real
`Ash.create` dispatch against `AshA2A.Test.Fixture.Item`
(`Ash.DataLayer.Ets`), postcondition observation, and commit -- under real
sustained concurrent load for a real bounded wall-clock window.

**Test**: `test/ash_a2a/chicago/stress/sustained_throughput_test.exs`
(`AshA2A.Chicago.Stress.SustainedThroughputTest`), tagged `@moduletag
:benchmark` (excluded from the default suite via `test/test_helper.exs`,
the same convention `test/ash_a2a/planning/goal_facts_density_benchmark_test.exs`
already uses). Run explicitly:

```
mix test test/ash_a2a/chicago/stress/sustained_throughput_test.exs --include benchmark
```

**Real collaborators throughout, no mocking**: a real, supervised
`AshA2A.ReceiptStore.Memory` `GenServer` (freshly started per run), a real
`AshA2A.Authority` struct per worker (`Authority.new/3`, the same
direct-attachment pattern `test/ash_a2a/command_bus_test.exs` and
`test/ash_a2a_command_bus_concurrency_test.exs` already use), and a real
`Ash.DataLayer.Ets`-backed `Item` resource. Every `command_id` and every
`Item.label` is genuinely distinct (`System.unique_integer/1`-suffixed per
dispatch) -- this run measures sustained throughput/latency/error-rate/
resource drift, not claim-collision arbitration (that is
`ash_a2a_command_bus_concurrency_test.exs`'s job, already covered
elsewhere).

### Real run configuration

Requested duration 12,000 ms, `System.schedulers_online() = 16` concurrent
real BEAM worker processes, each looping real `CommandBus.run/4` dispatches
continuously until the real deadline. One real warm-up `Ash.create` ran
before the timed window (documented ETS-table-manager-race avoidance, same
reasoning `ash_a2a_command_bus_concurrency_test.exs` already states).

real runs rather than collapsed into one cherry-picked number:

not inferred from the receipts alone; this held for all three runs.

### Real degradation pattern observed under sustained load

Samples were bucketed by their real wall-clock start offset into the
first half of each run's window vs. the second half, and each half's
latency distribution computed independently (reusing
`AshA2A.Chicago.Bench.distribution/1`, the same real statistics function
B1/B5/B9 use). **A real, measured latency-climbs-under-sustained-load
pattern is present in all three runs** -- median latency rose 26-44% and
p99 latency rose 1.7x-181x from the first to the second half of the same
12-second run, and the late-half sample count was always lower than the
early half (e.g. Run 1: 8,528 early vs. 5,576 late), consistent with real
per-request cost itself rising as each run progresses, not merely tail
noise.

Run 2 is the extreme case worth naming precisely: its late half collapsed
to 17 samples with a late-half p50 of 8,485,237 µs (8.5 seconds) --
several worker loops each spent multiple real seconds inside a single
`CommandBus.run/4` call late in that run. This is real, reproduced
evidence of tail-latency collapse under sustained load, not a rare/
theoretical concern.

This report does not assert one single proven root cause (a dedicated
profiling pass is out of this task's scope per its own instructions, and
fixing it is explicitly out of scope unless trivial -- it is not, given
the size of the effect). Real, disclosed candidates, stated as candidates
rather than conclusions:

- **Shared-host contention is a real, evidenced confound**, not a
  hypothesis: `uptime` read a load average of 12-18 on this 16-scheduler
  host during these runs, from other real, unrelated heavy processes
  (`ps` showed several near-100%-CPU Rust/Python builds). Run 2's outlier
  collapse most plausibly reflects a transient scheduling-starvation spike
  from that contention landing mid-run -- Run 3, taken moments later at a
  similar or higher reported load average, did NOT reproduce the collapse,
  which argues against steady-state load average alone predicting the
  effect and toward a transient contention event instead. This makes the
  degradation ratios above an honest but noisy signal on a busy shared
  host, not a clean isolated-host measurement.
- The real `Item` ETS table itself grows across each run (14,000-17,000+
  rows by the end, by design -- proving no cross-command contamination
  requires every row to remain), and `Ash.create`'s own real per-write
  cost on `Ash.DataLayer.Ets` is not asserted anywhere to be O(1) in table
  size.
- The real `AshA2A.ReceiptStore.Memory` `GenServer` accumulates one entry
  per command for the life of the run and is a single serialization point
  for every one of the 16 concurrent workers' claim/commit calls --
  mailbox queueing under 16-way real concurrent load, compounded by
  scheduler contention from the rest of the host, is a real candidate
  contributor to the specifically tail-heavy shape of the degradation
  (p99/max moved far more than p50 in every run).
- This test's own harness holds every real sample (a small map per
  dispatch) in each worker's local accumulator for the whole run and
  reverses it once at the end -- real memory the harness itself is
  responsible for, not attributable to the SUT.

A follow-up worth naming precisely: rerun this same file (unmodified) on
an otherwise-idle host to separate the SUT's own real degradation curve
from this session's real shared-host contention -- not attempted here
because this session had no idle window available.

### Real resource-drift signal (gross, not a precise leak proof)

`:erlang.memory/0` and `:erlang.system_info(:process_count)` sampled
immediately before the timed window and immediately after, Run 1 shown in
full (Runs 2-3 in the summary table above):

| | Before | After | Delta |
|---|---|---|---|
| Process count | 340 | 340 | **0** |
| Total VM memory | 102,030,176 B (~97 MB) | 272,921,194 B (~260 MB) | +170,891,018 B (~163 MB) |
| `:binary` | 4,281,608 B | 51,596,808 B | +47,315,200 B |
| `:processes` | 26,130,160 B | 144,801,288 B | +118,671,128 B |
| `:ets` | 2,441,912 B | 6,810,000 B | +4,368,088 B |

Zero net process-count growth in all three runs is a real, positive
signal: nothing leaked a supervised or unsupervised process across any of
the 34,881 total dispatches. Total VM memory delta scaled roughly with
each run's real dispatch count (Run 2 did the fewest dispatches and had
the smallest delta), consistent with the expected, by-design accumulation
this test intentionally keeps alive for its own end-of-run assertions
(every `Item` row, every receipt, every harness sample) rather than with
unbounded per-request growth independent of load -- but this test alone
does not isolate true steady-state per-request memory cost from that
by-design accumulation; a version of this test that discards/rotates
completed state during the run would be needed to do that, and was not
attempted here.
